whatIs: 従来の[バリューストリームマッピング](https://openpracticelibrary-ja.netlify.app/practice/vsm-and-mbpm/)と同様に、ラピッド・バリューストリームマッピングは[フローエンジニアリング](https://openpracticelibrary-ja.netlify.app/practice/flow-engineering)からのバリアントで、マップのアーティファクトをシンプル化し、[イベント・ストーミング](https://openpracticelibrary-ja.netlify.app/practice/event-storming/)とメトリクスベースのプロセスマッピングの強みを融合させて、2時間以内でフローとデータの「十分に良い」マップを素早く作成します。
whyDo: >-
  広範なマッピングに対するバイインや時間を得ることが難しいため、ラピッド・バリューストリームマッピングは一般的な状況に合わせて調整され、チームがすでにより生産性の低い取り組みのために確保している時間に収まるよう意図されています。


  ラピッド・バリューストリームマッピングはデジタルプロダクト開発とITの中で作られたため、デジタルネイティブ（最初のマップは実際にはGoogleスプレッドシートで作成されました——推奨しませんが！）であり、ビデオ会議とリアルタイム協働ホワイトボードを使うリモートワーカーに対応したマッピングに焦点を当てています。物理的な製造・トラック・倉庫に焦点を当てた従来のバリューストリームマッピングとは異なり、高度に不確実で適応的な環境での明確さを作る方法として、知識労働とテクノロジーの不可視の取り組みに焦点を当てています。


  マッピングにより、バリューストリームマッピングが提供するのと同じ利点が得られます：作業の共有可視性・意思決定をサポートするデータ・主要な制約またはボトルネックへのフォーカス。


  フローエンジニアリングの他のマップと組み合わせることで、初期のニーズや目標から、実行可能で・所有され・測定された次のステップまで、現在の作業フローの可視性と理解を作ることで、改善発見の素早く完全な実施が可能になります。


  ラピッド・バリューストリームマッピングは、単に可視性とフォーカスを作ることで、リードタイムを即座に20%削減することが一般的です。改善の取り組みと自動化を組み合わせると、プロジェクト・プロダクト開発・インシデント対応などの大きなバリューストリームのエンドツーエンドのリードタイムを60〜80%削減することが一般的です。


  同じプラクティスはあらゆるアクティビティのフローに使用できます：


  * 顧客または新入社員のオンボーディング

  * プロダクト開発

  * パートナー統合

  * 企業買収

  * インシデント対応

  * 営業プロセス

  * マーケティングキャンペーンの実施

  * イベント計画
howTo: >-
  このプロセスは**5つの独自のステージ**で構成されます。


  ## 1. ストリームの選択


  全てをマッピングすることはできません。このステップはチームを、目標アウトカム（達成したいこと）に最も関連した作業の特定のシーケンスにフォーカスさせます。


  ![Stream selection](/images/screenshot-2026-02-05-at-3.08.01-pm.png "Stream selection")


  \

  \

  **ファシリテーションのヒント：**


  * **顧客に固定する：** 「私たちのワークフローで定義された価値を受け取る顧客は、ターゲットアウトカムのサービスとして誰ですか？」と聞く。例えば、インシデント対応時間を短縮したい場合、問題のストリームとしてインシデント対応プロセスフローを使用します。

  * **境界を定義する：** ストリームの開始点と終了点に明示的に同意する。

  * **範囲を制限する：** ストリームが大きすぎる場合（例：「アイデアから現金まで」）、スライスする。ターゲットアウトカムを妨げているボトルネックを最も含みそうなセグメントに焦点を当てる。

  * **5Rs：** Paula Thrasherは効果的なバリューストリームの選択を確保するための5つの要素を強調しました。最近（Recent：最近の過去に起きた）・実際（Real：実際のビジネス価値を生み出すフロー）・到達（Reach：顧客がアウトプットを体験するところまで延びている）・実証済み（Road Tested：確立された運用中のもの）・代表的（Representative：関係するグループにとって典型的なフロー）であるべきです。


  ## 2. アクティビティのレイアウト


  これは作業を可視化します。目標は、*あるべき*ではなく、実際に何が起きているかの現実を捉えることです。フローの各アクティビティの短いタイトルを個別の付箋に書き、作業フローの完全なエンドツーエンドの表現として並べます。


  ![Activity layout](/images/screenshot-2026-02-05-at-3.07.44-pm.png "Activity layout")


  ![](/images/screenshot-2026-02-05-at-3.09.24-pm.png)


  \

  \

  **ファシリテーションのヒント：**


  * **逆から作業する：** 顧客/最終価値から始め、「この直前に何が起きますか？」と聞く。これにより見逃された分岐と「ハッピーパス」バイアスを防ぐ。

  * **動詞を使う：** 全ての付箋がアクションを表していることを確認する（例：「コードをレビューする」「アーティファクトをデプロイする」）。

  * **大まかに保つ：** 完璧主義を避ける。特定のステップの順序について議論が生じた場合、バリエーションとして記録して前に進む。


  ## 3. タイミングの追加


  これはマップに*フロー*の次元を追加し、時間が実際にどこで費やされているかと価値がどこで生み出されているかを明らかにします。**2つの主要なメトリクスを記録します：** 主に**サイクルタイム**（各アクティビティの開始から終了までの時間）と**ウェイトタイム**（キュー時間/遅延/待機時間）に焦点を当てます。


  ![Add timing](/images/screenshot-2026-02-05-at-3.10.31-pm.png "Add Cycle Time and Wait Time")


  \

  \

  **ファシリテーションのヒント：**


  * **摩擦が生じたら範囲を使う：** チームは正確な数字を求められると固まることが多い。「最良ケース/最悪ケース」を聞いて「状況による」の範囲を確立し、「最も多い場合」を押さえる。

  * **リードタイムを計算する：** 合計時間を合算して全期間を示し、効率ギャップ（プロセス時間/総リードタイム）を強調する。


  ## 4. その他の関連データの追加


  時間だけがコストではありません。このステップはシステムの摩擦を理解するために必要な追加のコンテキストを重ねます。時間が限られている場合は、後で記入することができます。


  * **情報フロー：** 役割・チーム・ツール・システム間のデータと情報のフローを記録する。承認・レビュー・相談・フィードバックループを考慮する。

  * **品質メトリクス：** **完了率と正確性（%C/A）**について聞く——「このステップは、明確化や修正なしに使用できる状態で作業を受け取る頻度は？」

  * **ツールとアーティファクト：** 作業が*どこで*行われるか（例：Jira・Slack・Excel）に注目して、コンテキストスイッチングとデータ交換を強調する。

  * **フラストレーションレベル：** 速くてもチームを疲弊させるステップに単純な指標（赤いドットや顔のアイコンなど）を使う。


  ## 5. 制約の強調


  マップの究極の目標は*主要な*ボトルネックを見つけることです。このフォーカスは、すでに制約されたアクティビティを過負荷にして状況を悪化させる取り組みを防ぎ、散漫と過剰な進行中作業を避けます。


  ![](/images/screenshot-2026-02-05-at-3.14.20-pm.png)


  \

  \

  **ファシリテーションのヒント：**


  * **フォーカス：** チームが現在フローを最も制限している*単一の*最大要因に同意するよう促す。

  * **狭く狙う：** 1つの遅延またはステージを強調することを目指す。常に拡大または詳細化できますが、多くに手を出しすぎると進捗のリスクになる。

  * **期待を設定する：** フォーカスしなければ、おそらく何も達成できない。素早い進捗と結果のために他の機会を意図的に脇に置いていることを明確にする。一度最初の結果が出れば、より多くの大きな課題に取り組める。


  発見したものに対処するには、依存関係マッピングで制約の原因を深く掘り下げるか、将来の状態バリューストリームマッピングでバリューストリームを再設計するか、フローロードマップに進みます。
